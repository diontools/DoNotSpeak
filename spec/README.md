# 仕様資料

このディレクトリは、DoNotSpeakの現行仕様、設計、互換性、品質基準、問題、対応計画、
監査記録、設計判断を管理する。資料の分類と更新方法はこのファイルを正本とする。

## 資料の分類

| 分類 | 役割 | 更新方針 |
| --- | --- | --- |
| 製品仕様 | ユーザーから見た正常な動作 | 現行動作に合わせて更新する |
| アーキテクチャ | 正常動作を実現する内部設計 | 実装と一致させる |
| 互換性 | Androidバージョンごとの差異と対応範囲 | 対応範囲の変更時に更新する |
| 品質管理 | ビルド、テスト、検証基準 | ツールや検証方法の変更時に更新する |
| 問題管理 | 現在把握している問題の台帳 | 発見から対応完了まで状態を更新する |
| 対応計画 | 複雑な問題の実装・検証計画 | 完了後も移動せず状態を更新する |
| 監査記録 | 特定時点の調査証跡 | 原則として内容を変更しない |
| 設計判断 | 方針を選択した理由と影響 | 変更時は新しいADRで置き換える |
| テンプレート | 新規資料のひな型 | 管理規則の変更時だけ更新する |

現行動作の正本は「製品仕様」と「アーキテクチャ」とする。対応計画や監査記録に記載された
将来案・過去状態を、現在の仕様として扱わない。

## メタデータ

`README.md`とテンプレートを除くMarkdown資料は、先頭に次のYAML frontmatterを持つ。

```yaml
---
title: 資料名
type: 製品仕様
status: 有効
created: 2026-08-16
last-reviewed: 2026-08-16
applies-to: d66b892
---
```

- キーは検証処理を安定させるため英語とする
- `title`の値、ファイル名、本文は日本語を基本とする
- `type`は上表の分類名を使用する
- `status`は`草案`、`有効`、`計画済み`、`対応中`、`検証待ち`、`完了`、`過去記録`、`廃止`から選ぶ
- `applies-to`には確認対象のコミットを記録する。監査記録では調査対象コミットとする

## 命名規則

- ファイル名とディレクトリ名は日本語を基本とし、空白を使用しない
- 問題IDは`AUD-001`形式で採番し、再利用しない
- 対応計画は`AUD-001_問題名.md`形式とする
- 設計判断は`ADR-0001_判断名.md`形式とする
- 監査記録は`YYYY-MM-DD_調査名.md`形式とする
- Android、Bluetooth、APIなど一般的な技術名称はそのまま使用する
- 行番号だけに依存せず、対象クラス・メソッド・確認コミットを記録する

## 問題管理の流れ

```text
未対応 → 計画済み → 対応中 → 検証待ち → 対応済み
                              ↘ 対応しない
```

1. 調査結果を[問題一覧](問題管理/問題一覧.md)へ登録する
2. 複数クラス、互換性、復旧処理などの検討が必要な場合だけ対応計画を作る
3. 実装開始時に問題一覧と対応計画の状態を更新する
4. 完了時に検証結果、修正コミット、現行仕様を同期する
5. 生のPlayレポートや認証情報はGit管理せず、対象期間・versionCode・集計結果だけを記録する

## Codexスキル

資料を追加・更新・整理するときは、リポジトリスコープの`$manage-project-specs`を使用する。
スキルはこの管理規則を読み、変更後にリンク、メタデータ、問題IDを検証する。

```text
$manage-project-specs 調査結果を問題一覧へ登録して
$manage-project-specs AUD-003の対応計画を作成して
$manage-project-specs spec全体を変更せずに検証して
```
