# サービス自動テスト基盤整備

## 背景

`DNSService`は、コマンドによる状態遷移、状態保存、音量制御、Alarm、Foreground Service通知、
WakeLock、Bluetooth判定、Tile更新を1クラスで処理している。主要処理はprivateメソッドからAndroid APIを
直接呼ぶため、OS状態や実時間へ依存せずに状態遷移と例外経路を再現する境界がない。

コミット`e1d09fb`時点では`src/app/src/test/`が存在せず、`app/build.gradle`の`testImplementation`も
コメントアウトされているため、`testDebugUnitTest`は`NO-SOURCE`となる。androidTestには次の検証がある。

- `SmokeTest`によるinstrumentationとshell commandの疎通確認
- `ScreenshotTest`による主要画面の取得
- `BluetoothPermissionServiceTest`によるBluetooth設定、実OS権限、初期化非待機、安全側音量0の検証
- `BluetoothPermissionFlowTest`による権限説明ダイアログのキャンセルからService開始までのE2E検証

Bluetooth権限経路はAUD-003で自動化されたが、`START`、`STOP`、`SWITCH`、sticky再作成、状態復元、
音量APIの`SecurityException`、Alarmの登録・取消を決定的に検証していない。AUD-001には
Foreground Serviceの起動要求・前景化拒否を強制するandroidTestが計画されているため、そのテスト境界を
本計画で重複実装せず、サービス全体の回帰テスト群へ統合する。

## 目標

- Android APIに依存しないサービス状態遷移をローカルUnit Testで高速かつ決定的に検証する
- 音量、時計、AlarmのOS呼び出しを狭い境界へ分離し、成功・拒否・例外をテストから再現できるようにする
- `START`、`STOP`、`STOP_UNTIL_SCREEN_OFF`、`SWITCH`、`APPLY_SETTINGS`、`REBOOT`、
  `SHUTDOWN`、null Intentの主要経路を自動検証する
- 音量操作の`SecurityException`でサービスが終了せず、再入防止状態も必ず解除されることを検証する
- 一時停止Alarmと定期確認Alarmの時刻基準、再設定、取消を実時間待機なしで検証する
- AUD-001のForeground Service拒否試験とAUD-003のBluetooth権限試験を、重複しない回帰テスト群として維持する
- ローカルUnit Testをpull requestと`master`・`dev`へのpushの品質ゲートにする
- テスト用差し替えがrelease動作を変更せず、各テストの終了後に確実に初期状態へ戻るようにする

## 対象外

- 実Bluetooth機器の接続、A2DP再生、SCO通話音声の自動化
- メーカー固有の音量制御、Foreground Service制限、Alarm遅延の再現
- Doze中の不正確なAlarmの実配信時刻を保証するテスト
- 通知画面と設定画面のスクリーンショット範囲拡大
- AUD-001で扱うForeground Service起動失敗の本体修正
- AUD-002で扱う外部公開Activityからの状態変更制限
- Unit Testを成立させるためにRobolectricでAndroid framework全体を模倣すること
- テスト件数やカバレッジ率だけを完了条件にすること

## 対応方針

### 1. 現行動作をテスト表へ固定する

実装前に、各コマンドの事前状態、次状態、永続化、音量更新、Alarm、Service終了の期待値を表にする。
少なくとも次を区別する。

| 入力 | 主な次状態 | 必須の副作用 |
| --- | --- | --- |
| `START` | 保護有効、一時停止解除、復帰時刻0 | 状態保存、出力更新、定期確認Alarm再設定 |
| `STOP` | 保護無効、指定時刻まで停止 | 状態保存、出力更新、一時停止Alarm設定、定期確認Alarm再設定 |
| `STOP_UNTIL_SCREEN_OFF` | 保護無効、画面消灯まで停止 | 状態保存、出力更新、定期確認Alarm再設定 |
| `SWITCH` | 有効なら画面消灯まで停止、無効なら開始 | 遷移先に対応する状態保存と出力更新 |
| `APPLY_SETTINGS` | 保護状態を維持 | 設定再読込、出力更新、定期確認Alarm再設定 |
| `REBOOT`またはnull Intent | 保存状態を復元 | 出力更新、定期確認Alarm再設定 |
| `SHUTDOWN` | Service非稼働 | Service停止、関連Alarm取消、Tile更新 |

この表は現行実装とAUD-001の確定済み方針を照合する。実装中に期待値が一致しない場合は、テストを
現在の偶然の挙動へ合わせず、問題一覧へ追加登録するか関連計画を更新して扱う。

### 2. 状態遷移をAndroid非依存のモデルへ分離する

`muteEnabled`、`stopUntilScreenOff`、`disableTime`を表すpackage-privateな状態モデルと、コマンドから
次状態を求める処理を`DNSService`から分離する。モデルは`android.*`をimportせず、時刻は`long`で受け取る。

ローカルUnit Testでは次を確認する。

- 初期状態からの`START`、時刻指定`STOP`、`STOP_UNTIL_SCREEN_OFF`
- 有効・無効それぞれからの`SWITCH`
- 保存値がある場合とない場合の`REBOOT`
- null Intentが`REBOOT`と同じ遷移になること
- `APPLY_SETTINGS`が保護状態を変更しないこと
- 不明なactionが状態を変更しないこと
- 各遷移で保存すべき`enabled`、`stopUntilScreenOff`、`disableTime`の組み合わせ

状態モデルはAndroid Serviceのライフサイクル、Toast、通知を担当しない。`DNSService`はIntentのactionを
モデルへ渡し、得た次状態を既存の保存・出力更新へ反映する。リファクタリング前後でユーザーから見た
コマンド動作を変更しない。

### 3. 時計とAlarm境界を分離する

現在の`SystemClock.elapsedRealtime()`と`AlarmManager`直接呼び出しを、製品実装と記録用fakeを持つ
package-privateな境界へ分離する。境界は少なくとも次を扱う。

- 経過時間の取得
- 時刻指定一時停止Alarmの登録と取消
- 1時間後を初回とする定期確認Alarmの登録と取消

テストではfake時計と記録用Alarm実装を使用し、次を待機なしで検証する。

- 定期確認の初回時刻が`elapsedRealtime + AlarmManager.INTERVAL_HOUR`
- 定期確認が`ELAPSED_REALTIME`、非Wakeup、不正確な1時間間隔であること
- 時刻指定停止がRTC基準で指定時刻へ登録されること
- 新しいコマンドの処理で既存Alarmが取り消され、必要なAlarmだけ再登録されること
- 明示停止で一時停止Alarmと定期確認Alarmが残らないこと

Androidの`PendingIntent`同一性と実配信はandroidTestまたは既存のエミュレータ確認で補い、ローカルUnit Testで
frameworkの内部実装を模倣しない。

### 4. 音量境界と例外経路を検証する

`AudioManager`の音量取得、直接設定、段階調整をpackage-privateな境界へまとめる。通常時は現行と同じ
`STREAM_MUSIC` APIへ委譲し、テスト時は現在音量の列、呼出履歴、`SecurityException`を返せるfakeへ
差し替える。

次をローカルUnit Testまたはdebug androidTestで検証する。

- 既に目標音量なら変更APIを呼ばない
- 直接設定では目標値を1回設定する
- 段階調整では上げ下げを選択し、目標到達時に終了する
- 音量が変化しなくても50回で終了する
- 音量取得、直接設定、段階調整の各`SecurityException`を捕捉し、呼び出し元へ送出しない
- 例外後も`volumeAdjusting`相当の再入防止状態が解除され、次の音量操作を実行できる
- 例外時に診断ログとユーザー通知の要求が1回だけ行われる

テストのために`AudioManager`自体を継承・模倣せず、アプリが使用する最小操作だけを境界にする。

### 5. Service統合androidTestを追加する

純粋な状態モデルと各fakeだけでは、Intent、SharedPreferences、Serviceライフサイクルへの接続ミスを
検出できない。debug APKのandroidTestから製品と同じ`DNSService`を起動し、記録Loggerとテスト境界を
使用して次を確認する。

- `START`、`STOP`、`STOP_UNTIL_SCREEN_OFF`、`SWITCH`で保存状態とService内状態が一致する
- `REBOOT`とnull Intent相当の再作成で保存状態が復元される
- `APPLY_SETTINGS`で保護状態を変えず、設定だけが再読込される
- 明示停止後にService、保存状態、一時停止Alarm、定期確認Alarmが残らない
- 音量例外後もServiceが稼働を継続する

テスト用setterをmain sourceへ置く場合はAUD-001と同じ規則を使う。

- package-privateかつ`BuildConfig.DEBUG`限定とする
- instrumentation threadとService main threadで共有する参照は`volatile`にする
- releaseビルドで差し替えようとした場合は例外にする
- `@After`とホスト側スクリプトの両方で既定実装へ戻す
- 固定sleepではなく、記録されたイベントを上限付きで待つ

テスト間ではService、SharedPreferences、設定、音量、Logger、境界の差し替えを初期化する。JUnitの
実行順、以前のアプリデータ、接続中の別エミュレータへ依存しない。

### 6. AUD-001・AUD-003との責務を整理する

AUD-001の実装では起動要求拒否と前景化拒否の差し替え境界、保存状態維持、Service停止、復旧通知失敗を
検証する。本計画ではその境界を作り直さず、`ForegroundServiceFailureTest`をサービス回帰テストの
実行対象へ含める。AUD-001実装前にも状態モデル、音量、Alarmの作業は進められるが、Service終了と
保存状態削除の最終期待値はAUD-001の実装後に統合する。

AUD-003のBluetooth権限試験は実OS権限とActivity経路を扱うため維持する。新しいfake Bluetooth層へ
置き換えず、サービス統合試験とは別にAPI 31・36で実行する。

### 7. CIへ段階的に組み込む

`android-build-check.yml`へ`testDebugUnitTest`を追加し、Lint、Debug APK、Unit Testを同じ必須ジョブで
実行する。失敗時にJUnit XMLとHTML reportをartifactへ保存し、`NO-SOURCE`を成功扱いにしない確認を
追加する。

Service統合androidTestは既存のAPI 31・36 matrixを利用する。Bluetooth権限を外側から切り替える試験と、
通常権限状態で実行するService試験をホスト側スクリプトで分け、失敗時はinstrumentation出力とLogcatを
保存する。全`connectedDebugAndroidTest`を暗黙に実行せず、対象classを明示して試験範囲を追跡可能にする。

## 実装順序

1. コマンド別の現行状態・副作用表を確定する。
2. JUnit依存関係を追加し、Android非依存の状態モデルとUnit Testを作る。
3. `DNSService`を状態モデルへ接続し、既存Bluetooth androidTestが変わらず成功することを確認する。
4. 時計・Alarm境界とfakeを追加し、一時停止と定期確認を待機なしで検証する。
5. 音量境界とfakeを追加し、通常、上限、`SecurityException`、例外後再実行を検証する。
6. Intent、SharedPreferences、Serviceライフサイクルを通す統合androidTestを追加する。
7. AUD-001の拒否試験を統合し、AUD-003のBluetooth権限試験と合わせてAPI 31・36で実行する。
8. ローカルUnit TestとService統合androidTestをCIへ追加する。
9. 変更した設計とテスト方針、問題一覧へ実装・検証結果を反映する。

## 検証計画

1. `testDebugUnitTest`を実行し、状態遷移、Alarm、音量の全Unit Testが成功し、`NO-SOURCE`でないことを
   Gradle出力とJUnit結果で確認する。
2. `assembleDebug`、`compileDebugAndroidTestJavaWithJavac`、`lintDebug`を成功させる。
3. API 31とAPI 36のクリーンAVDでService統合試験と既存Bluetooth権限試験を各3回連続成功させる。
4. 状態遷移処理を一時的に修正前相当へ戻し、対応するUnit Testが失敗することを確認する。
5. fake音量実装へ`SecurityException`を設定し、例外捕捉、Service継続、再入防止解除のassertionが
   修正前条件を検出することを確認する。
6. fake時計または初回時刻計算を修正前の絶対値へ一時的に戻し、AUD-005の回帰をUnit Testが検出することを
   確認する。一時変更はコミットしない。
7. AUD-001実装後は起動要求拒否と前景化拒否のandroidTestを実行し、保存状態維持とService停止を確認する。
8. CIでUnit Testが実行され、意図的な失敗を含む一時ブランチまたは一時PRでジョブが失敗することを確認する。
9. テスト終了後にService、Alarm、設定、音量、Logger、差し替え境界が残っていないことを確認する。
10. API 21へDebug APKをインストールし、境界追加によるクラスロード・互換性問題がないことを確認する。

- 音量取得、直接設定、段階調整の例外経路と例外後の再実行がテストされている
- 一時停止Alarmと定期確認Alarmの時刻基準、再設定、取消が実時間待機なしでテストされている
- Intent、保存状態、Serviceライフサイクルの接続をandroidTestで確認している
- AUD-001のForeground Service拒否試験とAUD-003のBluetooth権限試験を重複なく継続実行できる
- pull requestと`master`・`dev`へのpushでUnit Testが必須ゲートとして実行される
