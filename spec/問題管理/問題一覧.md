## AUD-003 Bluetooth権限不足時に初期化を待ち続ける

Android 12以降のランチャー起動でBluetooth権限ダイアログをキャンセルするか、設定画面へ移動した
場合、`USE_BLUETOOTH=true`のままサービス起動へ進むことがある。設定値とOS権限は別の状態であり、
両者が一致しないこと自体は異常ではないが、サービスが設定値だけを参照するとBluetoothプロファイルの
初期化を待ち続ける可能性がある。

- 対象: `DNSService.canUseBluetooth()`、`DNSService.isHeadsetConnected()`、`DNSService.isBluetoothInitialized()`、`DNSService.isBluetoothHeadsetConnected()`
- 対応: `applySettings()`は保存設定の読込だけに保ち、Bluetoothを実際に使う箇所で設定値と実権限を組み合わせる。権限がない場合は初期化を待たず、Bluetooth機器を非接続として扱う
- 診断: 設定無効時は`useBluetooth: false`、権限不足時は`BLUETOOTH_CONNECT permission: denied`、プロファイル待機時は`Bluetooth initialized: false`を区別して記録する
- 安全側動作: 権限不足時にBluetooth機器を判定できず音量が0になることを許容する
- 自動テスト: 実OS権限を使う拒否、設定無効、ダイアログキャンセル、許可のandroidTestを追加した
- 検証結果: API 31・36 AVDで4試験を各3回連続成功し、修正前条件では拒否ログ欠落によって試験が失敗することを確認した
- CI結果: GitHub Actions run [31940795652](https://github.com/diontools/DoNotSpeak/actions/runs/31940795652)でAPI 31・36がともに成功し、診断artifactを保存した
- 修正コミット: `1f74d3a`
- テストコミット: `3f98cf8`
- 検証計画: [Bluetooth権限不足時のエミュレータ検証](../対応計画/AUD-003_Bluetooth権限不足時のエミュレータ検証.md)
- 確認日: 2026-08-16

## AUD-004 通知設定と実動作が一致しない

「通知を使用」を無効にしてもOS権限と通知チャンネルは変わらず、ステータス通知もForeground
Serviceの要件として常に作成されるため、設定名から期待される動作と一致していなかった。

- 対象: `SettingActivity.onCheckedChanged()`、`DNSService.applySettings()`、`DNSService.createNotification()`
- 方針: `USE_NOTIFICATION`は権限要求の意向を保持する内部値として維持し、設定画面にはOSの実権限と
  各通知チャンネル状態を表示する。Foreground Serviceの通知生成処理は変更しない
- 対応: チェックボックスを通知状態表示と操作ボタンへ置き換え、権限要求とOS通知設定への導線を追加した。
  `DNSService`が通知ブロック状態変更Broadcastを受信し、ステータス通知が表示可能になった時点で
  現在状態の通知を再発行する。設定画面の`onResume()`は表示更新だけを行う
- 検証結果: Debug APKとandroidTestのコンパイルに成功した。Lintは既存箇所の8 errors / 33 warningsで
  失敗したが、変更ファイルへの指摘はない。API 36でレイアウト、権限・チャンネル状態、
  ボタン動作、通知再表示、権限拒否中のサービス継続を確認した
- 修正コミット: `6974177`
- 確認日: 2026-08-22
- 検討結果: [通知設定と実動作の整合対応](../対応計画/AUD-004_通知設定と実動作の整合.md)
- 初回監査: [2026-07-26 総合監査](../監査記録/2026-07-26_総合監査.md#4-通知を使用する設定が通知を無効化しない)

## AUD-005 定期確認Alarmの初回時刻が誤っている

`AlarmManager.ELAPSED_REALTIME`の`triggerAtMillis`へ、現在時刻を加えず1時間という絶対値を渡している。
端末起動から1時間以上経過している場合は過去時刻となり、設定直後にAlarmが発火する。

- 対象: `DNSService.setRebootTimer()`
- 方針: `SystemClock.elapsedRealtime() + AlarmManager.INTERVAL_HOUR`を初回時刻にし、
  `ELAPSED_REALTIME`、非Wakeup、不正確な繰り返しという現行の省電力特性は維持する
- 期待動作: サービスへの最新コマンドから少なくとも1時間は定期確認を発火しない。
  DozeやOSの一括処理による1時間以降の遅延は許容する
- 対応: 初回時刻を`SystemClock.elapsedRealtime() + AlarmManager.INTERVAL_HOUR`へ修正した
- 検証結果: API 36エミュレータの稼働時間3698秒で、修正前は過去時刻として登録された
  `PendingIntent`が`DNSReceiver.ACTION_REBOOT`まで実配信されることを確認した。修正後も製品と同じ
  1時間設定で、`origWhen=3644818`に登録された`PendingIntent`が稼働時間3843.7秒に実配信され、
  次回が1時間後へ更新された。直後発火がなく、再設定と明示停止時の取消も確認した
- 自動テスト: 本番と異なる時間値やテスト専用の注入経路を追加せず、実設定によるエミュレータ確認とした
- 修正コミット: `28cfb8b`
- 確認日: 2026-08-17
- 検討結果: [定期確認Alarm初回時刻修正](../対応計画/AUD-005_定期確認Alarm初回時刻修正.md)
- 初回監査: [2026-07-26 総合監査](../監査記録/2026-07-26_総合監査.md#5-定期アラームの開始時刻が絶対値になっている)

## AUD-007 Lintを品質ゲートにできない

2026-08-22にコミット`ca84f8b`で`lintDebug`を再実行し、8 errors / 33 warningsで失敗することを
確認した。エラーは次の3種類である。

- `MissingPermission` 6件: `DNSService.isBluetoothHeadsetConnected()`は直前にBluetooth設定と
  実OS権限を確認するが、Lintが`canUseBluetooth()`経由の確認を認識できない
- `NewApi` 1件: API 24で追加された`DNSTileService`のManifest宣言に対応APIが明示されていない
- `StartActivityAndCollapseDeprecated` 1件: `Compat.startActivityAndCollapse()`はAPI 34以上で
  `PendingIntent`版を使用するが、API 24–33専用分岐の`Intent`版がdeprecatedと判定される

- 方針: `MissingPermission`は事前の権限確認を維持し、Bluetooth API境界で`SecurityException`を
  捕捉して非接続へ縮退する。API分岐の指摘は対象を限定してLintへ意図を明示する。警告はAUD-009へ
  分離し、まずエラー0件をCIの品質ゲートにする
- 対応中: `DNSService.isBluetoothHeadsetConnected()`のBluetooth API境界で`SecurityException`を
  捕捉し、権限拒否ログを記録して`false`を返すようにした
- 途中検証: `lintDebug`の`MissingPermission` 6件が解消し、全体は残る2 errors / 33 warningsで失敗した
- 対応中: Manifestの`DNSTileService`宣言へ`tools:targetApi="24"`を追加した
- 途中検証: `NewApi` 1件が解消し、全体は残る1 error / 33 warningsで失敗した
- 対応中: API 24～33の`startActivityAndCollapse(Intent)`を専用メソッドへ分離し、レガシーAPIの
  1行だけへ`StartActivityAndCollapseDeprecated`の限定抑止を追加した
- 途中検証: `StartActivityAndCollapseDeprecated` 1件が解消し、`lintDebug`は
  0 errors / 33 warningsで成功した
- 途中検証: `assembleDebug`と`compileDebugAndroidTestJavaWithJavac`が成功した
- 途中検証: API 21 AVD `API_21_Android_5.0_Lolipop`へDebug APKをインストールし、
  `io.github.diontools.donotspeak.debug`のパッケージ登録を確認した
- 途中検証: API 26 AVD `Pixel_6_API_26_Without_GooglePlay`のQuick Settings Tile操作から
  `DNSTileService.onClick()`を経て`MainActivity`が起動し、クラッシュしないことを確認した
- 途中検証: API 36 AVD `Pixel_9_API_36_Android_16`のQuick Settings Tile操作から、API 34以上の
  `PendingIntent`版を経て`MainActivity`が最前面で起動し、クラッシュしないことを確認した
- 途中検証: API 31 AVD `DoNotSpeak_API_31`でBluetooth権限試験4件がすべて成功し、拒否時の
  安全側音量0、設定無効、ダイアログキャンセル、許可時に拒否と誤判定しないことを確認した
- 途中検証: API 36 AVD `Pixel_9_API_36_Android_16`でもBluetooth権限試験4件がすべて成功し、
  API 31と同じ拒否時・許可時の動作と試験後の後始末を確認した
- 静的確認: Bluetooth権限対象APIが`try`内にあり、`SecurityException`捕捉時に権限拒否ログを
  記録して`false`へ縮退する。既存の権限試験は事前確認で拒否するため捕捉経路自体は実行しない
- 対応済み: `.github/workflows/android-build-check.yml`を追加し、pull request、`master`・`dev`へのpush、
  手動実行で`lintDebug assembleDebug`を実行するようにした。レポートartifactは保存しない
- 途中検証: workflowのYAML構文と構造が有効であり、ローカル`lintDebug assembleDebug`が
  0 errors / 33 warningsで成功した
- 対応コミット: `9914846`
- 検証結果: `dev`へのpushで
  [Android Build Check run 32567063064](https://github.com/diontools/DoNotSpeak/actions/runs/32567063064)が起動し、
  GitHub Actions上の`lintDebug assembleDebug`が成功した。同じpushのAndroid CIも成功し、
  Android Emulator Testsは初回API 36ジョブの一時失敗後、失敗ジョブの再実行でAPI 31・36とも成功した
- 負試験: 一時PR [#45](https://github.com/diontools/DoNotSpeak/pull/45)へ意図的な`NewApi`エラーを追加し、
  [Android Build Check run 32568469636](https://github.com/diontools/DoNotSpeak/actions/runs/32568469636)が
  1 error / 34 warningsを検出して`:app:lintDebug`を終了コード1で失敗させることを確認した。
  一時PRはマージせず閉じ、検証用ブランチを削除した

## AUD-010 ローカル実機テストを対話的に実行できない

実Bluetooth機器、有線イヤホン、物理音量ボタン、画面消灯など、人が実機を操作しなければ成立しない
経路について、操作の待受け、操作指示、機械判定、後始末を一連で実行する仕組みがない。既存のADB
スクリプトはエミュレータのBluetooth権限状態を自動設定して実行するもので、実機操作を待って進行しない。

- 対象: `scripts/android/`、`src/app/src/androidTest/`、ローカル実機の検証手順
- 方針: serialを指定した実機専用runnerが、androidTestの待受け完了後に操作内容を表示し、実際の
  Broadcast、callback、音量、権限またはService状態を観測した時点で次の手順へ進む
- 安全性: Debug packageだけを操作し、成功・失敗・中断後に設定、音量、権限、Serviceを可能な範囲で復元する
- 計画: [ローカル実機対話テスト整備](../対応計画/AUD-010_ローカル実機対話テスト整備.md)
- 関連: [テスト方針](../品質管理/テスト方針.md)、
  [AUD-008 サービス自動テスト基盤整備](../対応計画/AUD-008_サービス自動テスト基盤整備.md)
